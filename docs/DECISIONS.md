## D-001. Территория v0.1 — Кром и Довмонтов город
- **Дата:** 2026-09-24 · **Статус:** Accepted
- **Контекст:** хочется всего Пскова, но это годы работы.
- **Решение:** только мыс при слиянии Великой и Псковы: Кром, Довмонтов город, ближайшие берега.
- **Почему:** самая узнаваемая и исторически насыщенная часть, даёт максимальный «вау» у псковичей при посильном объёме.

## D-002. Эпоха v0.1 — сегодняшний вид
- **Дата:** 2026-09-24 · **Статус:** Accepted; номер v0.2 — уточнение 2026-09-27
- **Контекст:** выбор между ~1500, ~1700 и современностью.
- **Решение:** сначала современный Кром, затем «откат» в ~1700 (v0.2) и ~1500 (v0.3).
- **Почему:** современный вид можно проверить глазами и фото с натуры, он калибрует масштаб и сразу узнаваем. Прошлое строится поверх как вариация.
- **Последствия:** архитектуру сразу делаем модульно, чтобы её можно было «переодевать» под эпохи. Заранее закладываем механизм вариантов (Data Layers или отдельные sublevel'ы по эпохам).
- **Уточнение 2026-09-27:** номер v0.2 отдан веб-версии (D-044, ROADMAP «v0.2. Веб-версия»); эпохам ~1700 и ~1500 новые номера не назначены.

## D-010. Интерфейс агента к редактору — встроенный Unreal MCP (UE 5.8)
- **Дата:** 2026-09-25 · **Статус:** Accepted (2026-09-25, проверено; см. «Факты после проверки» и D-011); роль MCP — уточнение 2026-09-27
- **Контекст:** управлять редактором через GUI (скриншоты и клики) медленно и хрупко.
- **Решение:** плагины `Unreal MCP` + `All Toolsets` (Experimental), HTTP-сервер `127.0.0.1:8000/mcp`. Основной агент — Claude Code, запущенный локально из `D:\PskovKrom` (видит `.mcp.json`, AGENTS.md, скрипты). Cowork-сессии — для планирования и документов.
- **Альтернативы:** (1) проксировать тот же MCP в Claude Desktop через `mcp-remote`, тогда он доступен и из Cowork; (2) community-MCP на Python Remote Execution (`runreal/unreal-mcp` и др.) для произвольного Python; (3) GUI через computer use — только для визуальной проверки.
- **Риски:** Experimental; без аутентификации (только loopback); может уронить редактор, поэтому чаще сохраняться и коммитить. Выполнение произвольного Python и скриншоты в документированных toolset'ах не заявлены: проверить `tools/list` после включения.
- **Факты после проверки (2026-09-25):**
  - Автостарт сервера: `bAutoStartServer=True` в `Krom/Config/DefaultEditorPerProjectUserSettings.ini` (по умолчанию выключен). Порт открывается примерно через минуту после запуска редактора.
  - `.mcp.json` лежит в корне репозитория, сервер называется `unreal-mcp`. Claude Code при первом запуске просит его одобрить.
  - Режим tool search: `tools/list` отдаёт только `list_toolsets`, `describe_toolset`, `call_tool`. Около 40 тулсетов подключаются по запросу: акторы, ассеты, материалы, сцена, Sequencer, PCG, логи, конфиги.
  - Скриншоты есть: `EditorToolset.EditorAppToolset.CaptureViewport` с камерой и сеткой-разметкой. Параметр `annotations` обязателен; чтобы выключить разметку, передаются нули.
  - Произвольного Python нет: `ProgrammaticToolset` запускает песочницу без `import unreal` (только json/math/re/…), это лишь склейка вызовов инструментов. Поэтому скрипты из `scripts\` запускаются иначе, см. D-011.
- **Уточнение 2026-09-27:** скрипты и правки сцены агент выполняет через Remote Execution (`scripts/ue_run.py`, D-011; STATE «Что есть»). Из MCP в работе два тулсета: `SlateInspectorToolset` — операции без Python API (D-015, `scripts/README.md` «Landscape: создание и обновление») и `EditorAppToolset.CaptureViewport` — его `view_krom.py` вызывает из Python редактора через `ue_run`, без HTTP-сервера (D-024).

## D-011. Скрипты редактора запускаются через Python Remote Execution (`scripts/ue_run.py`)
- **Дата:** 2026-09-25 · **Статус:** Accepted
- **Контекст:** встроенный MCP не выполняет код с `import unreal` (D-010), а наши генераторы (`blockout_krom.py` и т. д.) — обычные Python-скрипты редактора.
- **Решение:** в проекте включены `PythonScriptPlugin` и Remote Execution (`bRemoteExecution=True` в `DefaultEngine.ini`). `scripts/ue_run.py` через штатный `remote_execution.py` из движка находит открытый редактор с проектом Krom и выполняет в нём файл или строку кода: `python scripts/ue_run.py scripts/<имя>.py`. MCP используется для осмотра сцены, скриншотов и точечных правок.
- **Почему:** это штатный механизм Epic, без сторонних MCP-серверов. Скрипты остаются обычными файлами в git, их можно запустить и руками из Output Log.
- **Альтернативы:** community-MCP (`runreal/unreal-mcp` и др.) — лишняя зависимость при наличии штатного механизма.
- **Последствия:** Remote Execution слушает только loopback (multicast 239.0.0.1:6766, bind 127.0.0.1). Плагин `EditorScriptingUtilities` в UE 5.8 deprecated и не включаем: в скриптах используем editor subsystems (`EditorActorSubsystem` и т. п.) и `unreal.load_asset`.

## D-012. Подложка для масштаба — OpenStreetMap (геометрия) + спутник (сверка)
- **Дата:** 2026-09-25 · **Статус:** Accepted; подложка мешами — D-014, затем покрытие D-025
- **Контекст:** для M1 нужна подложка мыса в правильном масштабе, выровненная по северу.
- **Решение:** геометрию берём из OSM: выгрузка Overpass в `refs/osm/krom_<дата>.json` (bbox 57.8140–57.8300 N, 28.3120–28.3450 E, около 1.8 × 2.0 км) и полная геометрия водных объектов в `refs/osm/krom_water_<дата>.json`. Скрипт строит из неё геометрию в уровне: контуры зданий, городские стены, берега, улицы. Спутниковый снимок — только для визуальной сверки, в проект не импортируется. Музейные планы подключаются позже, для уточнения деталей.
- **Почему:** OSM — это векторные данные с открытой лицензией (ODbL), их можно импортировать скриптом и повторно выгрузить. Стены Крома (`barrier=city_wall`), собор (`way 39012954`), башни и берега там уже есть. Сгенерированные картинки (ChatGPT Images и т. п.) для подложки не годятся: нужна точная геометрия.
- **Альтернативы:** спутниковый снимок как текстура на плоскости (растр, лицензия неясна, ортотрансформация неизвестна); музейный план (точность и масштаб неизвестны, нужна привязка).
- **Последствия:** точность OSM — метры, не сантиметры. Контрольные размеры сверяем с REFERENCES. Атрибуция: «© участники OpenStreetMap, ODbL».

## D-013. Уровень `L_Krom` на World Partition; начало координат — центроид собора
- **Дата:** 2026-09-25 · **Статус:** Accepted
- **Решение:**
  - Основной уровень — `/Game/Krom/Maps/L_Krom`, World Partition. Территория около 2 км, всё держим загруженным: у сгенерированных акторов `is_spatially_loaded = False` (флаг `bEnableStreaming` из Python недоступен). Создаётся и обновляется скриптом `scripts/level_krom.py`, он же стартовый уровень редактора и игры. Шаблонный `Lvl_FirstPerson` не трогаем (D-009).
  - **Начало координат по X/Y** — центроид контура Троицкого собора в OSM (`way 39012954`): **57.8221102 N, 28.3289529 E**. X — на истинный север, Y — на восток, 1 uu = 1 см.
  - **Z = 0** — уровень земли у собора. Абсолютную отметку (м над уровнем моря) уточним вместе с рельефом.
  - Пересчёт широты и долготы в метры — локальная касательная плоскость с радиусами кривизны WGS84 в точке начала координат (`scripts/krom_geo.py`). На 1–2 км ошибка — сантиметры.
- **Почему:** Data Layers для эпох (D-002) работают только в World Partition. One File Per Actor удобен для git. Центроид по OSM воспроизводим, его можно пересчитать тем же скриптом.
- **Альтернативы:** обычный уровень с sublevel'ами для эпох (проще, но без Data Layers); начало координат в центре bbox или по крестам (не воспроизводимо).

## D-014. Рельеф — FABDEM + берега по OSM → Landscape 2 × 2 км; подложка — текстура на Landscape
- **Дата:** 2026-09-25 · **Статус:** Accepted (уточняет D-012 и D-013); подложка — D-025, переимпорт высот — D-026, берег Псковы — D-037, D-039
- **Контекст:** M1 требует рельеф мыса и берега Великой и Псковы. Открытых DEM точнее 30 м на Псков не нашли. Python API UE 5.8 не умеет создавать Landscape (только менять высоты у существующего через render target).
- **Решение:**
  - **Высоты суши — FABDEM V1-2** (Copernicus GLO-30 без зданий и леса, шаг 1″ ≈ 31 × 16 м, лицензия некоммерческая — у нас не коммерция). Кроп: `refs/dem/fabdem_krom.tif`.
  - **Берега строит скрипт** `terrain_krom.py`. Береговая линия — вода из OSM. У воды DEM не используется: там вода выровнена в 27–28 м и размазывает берег на 1–2 клетки. Плато продолжается от суши, откос — smoothstep шириной 35 м. У городских стен откос сжимается так, чтобы бровка пришлась на стену (≥ 10 м). Русло — до 4 м глубиной.
  - **Z = 0 ↔ 43,15 м абс.** (FABDEM, геоид EGM2008) — земля у собора, как в D-013. **Урез — 30,0 м абс.** (гидропост) → Z = −13,15 м.
  - **Landscape:** 2017 × 2017 вершин, шаг 1 м, 16 × 16 компонентов по 2 × 2 секции × 63 квада. Центр — в начале координат, угол в (−1008, −1008) м. Scale 100, то есть 1/128 м на ступень heightmap. World Partition: 64 прокси. Создаётся в режиме «Ландшафт» → «Импорт из файла» (процедура — `scripts/README.md`); агент делает это сам через интерфейс (D-015).
  - **Подложка OSM — текстура** `T_KromMap` 2048² (≈1 м/пиксель) в материале `M_KromLandscape`, UV берутся по мировым XY. Плоские меши `underlay_osm.py` удалены вместе со скриптом. Источник геометрии по-прежнему OSM (D-012).
  - **Вода** — плоскость 2016 × 2016 м на Z = −13,15 м, материал `M_KromWater`, без коллизии (`landscape_krom.py`).
- **Почему:** Landscape — штатный инструмент движка: кисти, трава, PCG, Water plugin, слои редактирования. Свой меш-рельеф пришлось бы дорабатывать под всё это самим. FABDEM сходится с независимой отметкой: медиана плато Крома 43,6 м при репере 43,82 м БС (S-17).
- **Альтернативы:** Copernicus GLO-30 / SRTM — это DSM: крыши и кроны поднимают плато на 4–5 м. Ручная лепка — не воспроизводима. Меш-рельеф из скрипта (GeometryScript / glTF) полностью автоматический, но без кисти и травы.
- **Последствия:** форма откосов — модель, а не измерение; до сверки с фото это гипотеза. После правки `terrain_krom.py` heightmap переимпортируется через режим «Ландшафт» → «Управление» → «Импорт» (скриптом — в IDEAS). Лицензия FABDEM некоммерческая: если цели проекта изменятся, пересмотреть.

## D-016. Blockout: план в `krom_plan.py`, примитивы на рельефе по трассам, снимки через SceneCapture
- **Дата:** 2026-09-25 · **Статус:** Accepted
- **Контекст:** M2 требует blockout стен, башен, собора, колокольни и Довмонтова города. Башни Крома в OSM не размечены, стены — линии по внешней грани. Те же положения и размеры понадобятся в M3 (сплайн-стена, герои).
- **Решение:**
  - **План — отдельный чистый модуль** `scripts/krom_plan.py` без `unreal`: башни и здания как наборы примитивов в осях здания (`Building` / `Part`), стены как участки «башня — башня» (`WallRun`). У каждой цифры есть источник из REFERENCES или пометка «гип.». Это единственное место, где записаны положения; скрипты редактора их только читают.
  - **Центры башен** берутся по петлям и выступам, которыми линии стен OSM обходят башни. Если петли нет — по контуру OSM или точке Wikidata (расходится на 4–9 м). Спутник служит только для сверки (D-012).
  - **Стены** — линии OSM `barrier=city_wall`, разрезанные контурами башен (с допуском 0,5 м). Конец линии ближе 4 м к башне дотягивается в её центр.
  - **Blockout** (`blockout_krom.py`) собирается из StaticMeshActor на `/Engine/BasicShapes` и пирамиды `SM_BO_Pyramid4`, созданной через GeometryScript. Материал — `M_Blockout` с цветом-параметром. Высоты земли снимаются трассировкой по Landscape до того, как появятся новые акторы. У стены верх = более высокая сторона + высота со двора, низ — на 1 м ниже самой низкой земли под ней. Стена режется на коробки не длиннее 6 м.
  - **Снимки из скриптов** — `shot_krom.py`: SceneCapture2D → render target → PNG. Ракурсы-кандидаты стоят как CineCameraActor (`cameras_krom.py`).
- **Почему:** данные отделены от расстановки, поэтому план проверяется без редактора и переиспользуется в M3. Трассировка сажает blockout на тот Landscape, который есть, и не требует читать PNG в Python редактора (там нет numpy/PIL).
- **Альтернативы:** DynamicMeshActor из GeometryScript на каждый участок стены (меньше акторов, но без distance field, и Lumen их не видит); только точки Wikidata (смещение до 9 м); `HighResShot` (в фоне вьюпорт не рисуется, файл не пишется); `CaptureViewport` из MCP (1–2 МБ base64 в контекст агента).
- **Последствия:** ≈360 акторов, после правки плана скрипт перезапускается целиком. В снимках SceneCapture нет Lumen, тени чёрные: годится для проверки геометрии, но не для красивых кадров (для них MRQ в M6).

## D-017. Фото-референсы — Wikimedia Commons со свободными лицензиями; сверка «фото / модель» с точки съёмки
- **Дата:** 2026-09-25 · **Статус:** Accepted (дополняет D-012)
- **Контекст:** собственных фото с натуры (S-04) нет, а Кром снят в интернете с любых ракурсов. Нужны референсы, которые можно хранить в репозитории и показывать, и способ сравнивать с ними модель, а не «на глаз».
- **Решение:**
  - Фото берём **только с Wikimedia Commons и только со свободными лицензиями** (CC BY / BY-SA / FAL / PD). Скрипт `scripts/photo_refs.py fetch` скачивает список `PHOTOS` (превью 1600 px) в `refs/photos/commons/`. Манифест `manifest.json` хранит автора, лицензию, ссылку, дату, точку съёмки и фокусное из EXIF. При любом показе подписываем автора и лицензию.
  - **Сверка:** `shot_krom.shot_photos()` снимает модель из точки съёмки каждого фото. Угол обзора считается из фокусного в пересчёте на 35 мм, пропорции кадра совпадают с фото. Цель камеры, отметку глаза (мост, дрон, вода) и фокусное, если его нет в EXIF, задаём в `PHOTOS` руками. `photo_refs.py compare` склеивает пары «фото | модель» с подписью в `media/renders/compare/`.
  - Пропорции по фото — это замер с пометкой ±, а не факт: масштаб берём по известной отметке (яблоко главы, 55 м колокольни). Геотеги на Commons бывают неточными на десятки метров.
- **Почему:** на Commons тысячи снимков, у многих есть camera location и EXIF, лицензии понятны. Снимки из поиска и соцсетей с неясными правами в репозиторий не кладём. Сравнение с той же точки показывает расхождения пропорций, которых на глаз не видно.
- **Альтернативы:** свои фото с натуры (лучше всего, остаются желательными для M4 и материалов); Яндекс/Google-панорамы (права не позволяют хранить и показывать); спутник (только план, D-012).
- **Последствия:** `refs/photos/commons` через LFS (~6 МБ). Список фото растёт по мере надобности, например для героев M3.

## D-018. Герои — в Blender скриптами (bpy, без окна), стены — в UE; Blender — инструмент агента
- **Дата:** 2026-09-25 · **Статус:** Accepted (стены уточнены в D-021: скрипт, не Blueprint со сплайном)
- **Контекст:** M3 — детальные собор, колокольня и башни. Выбор между Blender и Modeling Mode в UE. Владелец в Blender не работал и не планирует, так что моделирует агент скриптами. Сравнивались bpy и GeometryScript.
- **Решение (гибрид):**
  - **Стены** (`BP_KromWall`) остаются в UE: сплайн + GeometryScript/PCG по `krom_plan.WallRun` и рельефу. Им нужны сотни метров, рельеф и данные OSM.
  - **Герои** (собор, колокольня, башни, палаты) делаются в **Blender 5.2 LTS** скриптами `scripts/blender/*.py` через `python scripts/bl_run.py …` (`--background --factory-startup`). Выгрузка — glTF (`.glb`) в `build/blender/` (не в git), импорт в UE скриптом (Interchange, Nanite). Источник правды — скрипты, `.blend` не храним. Положение героя в сцене задаёт `krom_plan` (origin, yaw); в Blender моделируем в осях здания.

  - Превью Workbench рендерится из того же скрипта за ≈5 с — нагляднее снимков SceneCapture.

- **Альтернативы:** всё в UE на GeometryScript (один инструмент, но беднее и нестабильнее); ручное моделирование владельцем (не планируется); готовые ассеты с Fab (Крома там нет).
- **Последствия:** два инструмента и шаг импорта. Импорт героев в UE будет отдельным скриптом, по образцу пробного. Blender обновляем осознанно, в пределах LTS.

## D-019. Конвейер героя: план в `krom_plan`, генератор в Blender, `heroes_krom.py` в UE, снимки в тиках редактора
- **Дата:** 2026-09-25 · **Статус:** Accepted (уточняет D-016, D-018); материалы героев — D-027
- **Контекст:** первый герой — Троицкий собор. Размеры нужны и blockout, и детальной модели. Пробный импорт показал, что Interchange строит один выпуклый корпус коллизии и оставляет в запасном меше Nanite ≈6 % треугольников. SceneCapture рисует Nanite только грубыми кластерами, если захват идёт прямо в Python-команде: окна пропадают, луковицы выходят кубами.
- **Решение:**
  - **Размеры героя — в `krom_plan`** (для собора `TrinityPlan` / `TRINITY`): массы, высоты, главы, контрфорсы, у цифр источники. Blockout (`cathedral()`) и генератор Blender (`scripts/blender/cathedral.py`) читают одни и те же числа. В генераторе — только пропорции деталей (окна, наличники, пояса, аркатура, профиль луковиц).
  - **Генератор** строит замкнутые тела в осях здания (помощники `bl_krom`: `Frame`, `extrude`, `lathe`, `hip_roof`, `slab`). Проёмы вырезаются булевой операцией, решатель Manifold, один вырез на тело. Всё склеивается в один меш со слотами по ключам `krom_plan.COLORS`, развёртка «кубом» 1 UV = 1 м.
  - **`heroes_krom.py`:** у здания есть `Building.hero` (путь StaticMesh). Скрипт импортирует `build/blender/<имя>.glb` во временную папку. Первый раз меш переносится на место. Дальше геометрия копируется в тот же ассет (GeometryScript), ссылки не рвутся. Материалы пока `MI_BO_<Ключ>`. Коллизия — «complex as simple». Запасной меш Nanite — 100 % треугольников. Актор ставится в origin/yaw на землю. `blockout_krom.py` здания с готовым героем пропускает.
  - **`shot_krom.shot()` ставит снимок в очередь**, захват идёт в post-tick callback редактора. `photo_refs.py compare` ждёт файлы.
- **Почему:** один источник чисел — правка размера не расходится между blockout и героем. Полный запасной меш нужен для коллизии прогулки (M5) и для снимков; на 3060 он дешёвый (≈92 тыс. треугольников). Копирование в существующий ассет надёжнее, чем удаление и переименование: удаление мешает транзакционный буфер редактора.
- **Альтернативы:** держать размеры в самом генераторе (дубли с blockout); импорт прямо в итоговую папку (Interchange раскладывает по подпапкам `StaticMeshes/`, `Materials/` и создаёт MI на каждый слот); выключить Nanite у героев (против D-005).
- **Последствия:** снимки из скриптов асинхронные: файл появляется через несколько кадров, пока он не появился — снимок не готов. Для нового героя нужны dataclass плана в `krom_plan`, генератор в `scripts/blender/` и поле `hero` у здания.
- **Уточнение 2026-09-25 (колокольня):** нуль высот здания — земля в `Building.ground_at`, это точка `base`, если задана, иначе `origin`. Актор ставится в `origin`/`yaw` на эту высоту, так делают и `heroes_krom.py`, и `blockout_krom.py`. У колокольни `base` — двор у фасада пристройки, от него сняты отметки по фото. Общие детали генераторов (`Openings`, `band`, `cornice`, `ngon`, `loft`, материалы `M`) лежат в `bl_krom`.

## D-021. Стены — скрипт редактора `walls_krom.py` (GeometryScript → StaticMesh), профиль — данные в `krom_plan`
- **Дата:** 2026-09-25 · **Статус:** Accepted (уточняет D-018: вместо Blueprint `BP_KromWall` со сплайном — скрипт)
- **Контекст:** последний пункт M3 звучал как «сплайн-стена `BP_KromWall`: зубцы/кровля, башни в узлах, ворота». Blueprint строил бы стену в construction script, то есть в DynamicMesh. У DynamicMesh нет distance field, и software Lumen его не видит (D-016). Логика жила бы в графе, а не в тексте в git. Сплайн тоже ничего не даёт: трассы — `WallRun` из OSM, руками их никто не правит. Зубцов у стен Крома на фото нет (REFERENCES, «По фото S-25»). Выбор инструмента владелец доверил агенту.
- **Решение:**
  - **Инструмент.** `scripts/walls_krom.py` — Python редактора (D-011) с GeometryScript. На каждый `WallRun` — свой StaticMesh с Nanite. Как у героев (D-019): запасной меш 100 %, коллизия complex as simple, развёртка кубом 1 UV = 1 м. Слоты — ключи `COLORS`: тело и бруствер `stone`, кровля, столбы и настил `wood`. Земля — трассировкой по Landscape, как в blockout. Акторы с тегом `generated:walls_krom`. Булевы операции нужны только для проходов, бойницы — промежутки между блоками бруствера.
  - **Профиль.** Тело из плитняка. По внешней грани идёт сплошной бруствер с бойницами, за ним открытый боевой ход; где ход шире тела, настил лежит на консолях. По внутреннему краю хода стоят столбы, над ходом — односкатная тёсовая кровля со скатом во двор и свесом за столбы. Числа — `WallProfile` у каждой стены в `krom_plan.WALLS`: толщина, ширина хода (S-23: западная 1,52, восточная 2,2), высота кладки со двора (S-23: 6–8 м), подъём кровли (S-23: с кровлей 7,4–9,4 м), размеры бруствера и шаг столбов и бойниц (по фото, гип.). Стены Довмонтова города и Захаб — тот же профиль с другими числами (гип.). Профиль можно переопределить на отдельном участке: например, Кутекрома — Плоская лежит в том же way, что западная стена, но это, вероятно, стена Окольного города (REFERENCES).
  - **Положение.** Линия OSM — внешняя грань (D-016), тело уходит от неё во двор. Сторона двора задаётся у стены явно, самопроверка — двор выше. В blockout коробка стоит по оси линии, поэтому новая стена сдвинута внутрь на полтолщины.
  - **Рельеф.** Верх идёт звеньями с горизонтальной кровлей и ступенями между ними, как на фото. Звено держит отметку «земля двора + высота», пока земля двора не уйдёт на ступень (≈0,5 м, гип.). Низ звена — на 1 м ниже самой низкой земли под ним, как в blockout. Высота считается от двора, поэтому снаружи стена выходит выше сама — у Персей и над реками.
  - **Высоты сверяются с фото** (D-017): `kutekroma_yard`, `belfry_yard` и кадры с Завеличья. Если высота со двора расходится с фото больше чем на 1 м, она правится в плане, при нужде — поправкой на участке трассы. Так закрывается и блокер у Кутекромы.
  - **Стыки.** Стена входит в контур башни и кончается внутри: у всех башен тело выше кровли стены. Пристройка колокольни стоит в линии стены и несёт её свес (`belfry.annex`, D-019). Поэтому стены режет контур столпа вместе с пристройкой, а кровля стены подходит к свесу на его высоте (≈6,7 м от двора). Лестницы на ход у Кутекромы — не в этой итерации (IDEAS), проём там — один из проходов ниже.
  - **Проходы** — данные плана: место на трассе берётся по узлу OSM, где через стену идёт дорожка, ширина и высота арки — по фото. Сейчас их два: в Персях у Троицкой башни и в восточной стене у Кутекромы (REFERENCES). Ворота в башнях (Рыбницкая, Власьевская) делаются вместе с башнями.
  - **Blockout.** Если меши стен есть, `blockout_krom.py` коробки стен не ставит, а `walls_krom.py` удаляет уже стоящие — так же, как с героями.
- **Почему:** StaticMesh с Nanite видит Lumen. Рельеф берётся из самого уровня, поэтому после правки Landscape достаточно перезапустить один скрипт. Импорта нет. Профиль в данных: переодеть стены под эпоху (D-002) — значит поменять числа. Звенья со ступенями похожи на фото и проще в геометрии: звено — это выдавленный профиль.
- **Альтернативы:** (1) Blueprint со сплайном, как было в ROADMAP, — Lumen его не видит, граф не хранится в git текстом. (2) PCG и модульный набор (прясло, столб, кровля) — переменная высота и ступени плохо ложатся на модули; PCG ещё пригодится в M5. (3) Blender по конвейеру героев: `bl_krom` с `Openings`, `slab`, `box_uv`, превью за 5 с, рельеф из `refs/dem/heightmap_L_Krom.png`. Для мелких деталей это дешевле, но рельеф берётся из файла, а не из уровня, и добавляется шаг импорта. В v0.1 стена в основном в кадре с реки, мелочи там не видны. (4) Оставить коробки — M3 не закрывается, стена у Кутекромы остаётся выше настоящей.
- **Факты (проверено в редакторе 2026-09-25, UE 5.8.3):** есть `GeometryScript_Primitives.append_sweep_polygon`, `append_simple_swept_polygon`, `append_simple_extrude_polygon`, `GeometryScript_MeshBooleans.apply_mesh_boolean`, `GeometryScript_UVs.set_mesh_u_vs_from_box_projection`, `GeometryScript_Materials` (material ID треугольников). для Nanite при создании ассета есть опция `GeometryScriptCreateNewStaticMeshAssetOptions.enable_nanite` (по умолчанию выключена; в деле не проверена).
- **Последствия:** пункт M3 в ROADMAP переименован. Трассировка земли теперь в трёх скриптах (blockout, heroes, walls) — при случае вынести её в общий модуль. После правки Landscape перезапускать `walls_krom.py`.
- **Уточнение 2026-09-25 (реализация):**
  - Геометрию строит чистый модуль `scripts/wall_mesh.py` (без `unreal`, проверяется без редактора). `walls_krom.py` только снимает землю и передаёт сетку в GeometryScript одним вызовом `append_buffers_to_mesh` на материал. Булевы операции не понадобились и для проходов: проём — это тело, разрезанное на куски, свод арки — 8 граней.
  - Бруствер доходит до самой кровли, как на фото. Первая версия с зазором 1,4 м между бруствером и коньком (буквальное прочтение S-23 «кладка 6–8, с кровлей 7,4–9,4») давала небо сквозь ход, на фото его нет. Поэтому `h` — конёк (S-23 «с кровлей»), а уровень хода выводится из высоты у столбов 2,1 м и уклона 25°: западная — 5,0 м, восточная — 4,7 м от двора.
  - Ступень — 1 м. При 0,5 м на склоне у Плоской ступени шли через каждые 6 м и выходила лестница.
  - Проёмы (`WallGate`) бывают четырёх видов: сквозной проход; дверь — сквозная арка с дощатой створкой; заложенная арка — ниши с обеих сторон; ниша только со двора (амбразура). Место задаётся узлом OSM или расстоянием по стене от башни. Владелец напомнил, что проходов в стене больше двух. Агент-исследователь нашёл их по актам ГИКЭ 2016 и 2026, OSM и фото Commons (REFERENCES, S-30). В модели пять проходов и дверей и 11 ниш амбразур подошвенного боя в западной стене; шаг ниш — гипотеза.
  - Концы у башен продлены на 2 м, у пристройки колокольни — на 1 м. Перси толще Довмонтовой и Троицкой башен, их торец выходит из-за башен на 2–3 м — так и оставлено.
- **Уточнение 2026-09-25 (стыки и двор):**
  - Т-стыки стен — данные плана `JOINS` (`WallJoin`). Конец линии OSM, который упирается в соседнюю стену, а не в башню, продлевается в её тело на 1 м (`JOIN_IN_M`). Если рядом проём — по его откосу, чтобы не закрыть проезд. Имя участка остаётся «конец», ассеты не меняются. Так закрыты две сквозные дыры по ≈4 м: захаб — Перси у Великих ворот и южная стена Довмонтова города — западная у Власьевской. В OSM там стены толще, чем в модели, и линии друг до друга не доходят.

## D-022. Горизонт — кольцо рельефа за пределами Landscape, в M4 вместе с туманом
- **Дата:** 2026-09-25 · **Статус:** Accepted (переносит идею «Горизонт за пределами 2 км» из IDEAS в M4)
- **Контекст:** Landscape и вода — квадрат 2 × 2 км (D-014), за ним пусто. Ниже горизонта SkyAtmosphere рисует землю планеты — ровную тёмно-синюю плоскость, и в облёте мир выглядит островом в море. С Завеличья край мира попадает в главный ракурс.
- **Решение:** в M4 вместе с атмосферой и туманом сделать кольцо рельефа вокруг Landscape — низкополигональный меш из FABDEM на несколько километров, чем дальше, тем грубее. Берега и реки в кольце берутся по DEM, без правки по OSM. Высотный туман настраивается так, чтобы кольцо растворялось в дымке. Радиус, шаг сетки, вода и материал решаются в начале M4.
- **Почему:** дымку на горизонте настраивают под то, что там стоит. Без кольца все пробы света в M4 будут на «острове». Владелец согласен: «так всяко лучше, чем остров».
- **Альтернативы:** (1) только туман — край прячется, но в ясный день пустота в дымке за городом выглядит неестественно; (2) оставить до M5 — все пробы света M4 на острове; (3) увеличить Landscape — больше heightmap и VRAM, а детали вдали не нужны (D-005, D-014).
- **Последствия:** нынешний кроп FABDEM (`terrain_krom.DEM_CROP_BOUNDS`) выходит за Landscape всего примерно на километр, нужен кроп шире (тайл N57E028 скачивается скриптом целиком). Вода за краем Landscape — отдельный вопрос M4: реки уходят за 2 км.

## D-023. Кольцо горизонта — круг 18 км из FABDEM, Nanite-меш, покрытие ESA WorldCover
- **Дата:** 2026-09-25 · **Статус:** Accepted (уточняет D-022: радиус, сетка, вода, материал)
- **Контекст:** D-022 отложил параметры кольца на начало M4. Вокруг Пскова равнина: в 25 км от собора отметки 27–97 м, медиана 49 м. Рельефа с земли почти не видно, кольцо закрывает пустоту за краем и показывает, куда уходят реки и где начинается озеро (дельта Великой — в 10–12 км к северо-западу, берег Псковского озера — в 15–20 км). Геометрический горизонт с `zavelichye` — 22 км, с `oblique` — 70 км, поэтому до настоящего горизонта кольцо не дотянется ни при каком разумном радиусе: его край должна закрыть дымка. Тайл FABDEM N57E028 кончается в 19,5 км к западу и в 19,8 км к северу от собора. Выбор радиуса и материала — владельца, построение — агента (как в D-021).
- **Решение:**
  - **Размер.** Круг радиусом 18 км с центром в начале координат, без квадрата Landscape. Помещается в один тайл FABDEM, в нём дельта и южный берег озера. Высотный туман в самом ясном пресете полностью закрывает землю к 18 км: радиус кольца и есть видимость ясного дня.
  - **Построение** — в два шага, как рельеф (D-014): скрипт в `.venv` строит сетку и маску покрытия из FABDEM и WorldCover, скрипт редактора собирает из сетки StaticMesh с Nanite через GeometryScript, как стены (D-021). Без коллизии и без distance field, всегда загружен (не стримится World Partition), акторы с тегом `generated:<скрипт>`. Сетка — Delaunay по точкам с шагом 24 м у Landscape, 48 м дальше 2,5 км и 96 м дальше 6 км (≈370 тыс. треугольников, ассет ≈11 МБ). Упрощение на экране делает Nanite; редкая сетка вдали нужна не ему, а размеру ассета в LFS: равномерная сетка 30 м — ≈2 млн треугольников. Скрипты — `horizon_mesh.py` и `horizon_krom.py`.
  - **Кривизна Земли.** Высоты опускаются на d²/2R, R — радиус планеты SkyAtmosphere (у 18 км — на ≈25 м). У края Landscape кривизны нет, она нарастает на тех же 400 м, что и переход к FABDEM.
  - **Стык с Landscape.** Кольцо заходит под край Landscape. Под Landscape (48 м) оно на полметра ниже его, у края высоты берутся из `heightmap_L_Krom.png` и на 400 м переходят в FABDEM, так что ступеньки на краю нет.
  - **Вода.** Изогнутая плоскость на урезе (30,0 м абс.) по всему кругу, отдельно от плоскости воды Landscape. В FABDEM вода выровнена в 27–28 м, поэтому озеро и низовья рек (Великая — до ≈10 км к югу, Пскова — до ≈4 км к востоку) проступают сами. Суша по DEM ниже уреза (28,9–30,3 м, ≈1,3 % круга, почти всё в дельте) поднята на 0,3 м над урезом: иначе плоскость заливала бы острова дельты. Реки выше уреза рисует материал по классу «вода» WorldCover.
  - **Материал.** Маска покрытия ESA WorldCover 2021 (10 м, S-31): четыре канала — лес (с кустарником), поле и луг, город (с голым грунтом), вода и болото. Цвета групп — параметры материала, их сводят с травой и землёй Landscape и подстраивают под время суток. Specular у суши 0,1: при 0,5 блик неба под скользящим углом красил лес вдали в лиловый. Текстура до 4K (≈9 м на тексель, ≈22 МБ VRAM) — исключение из D-005, как у героев; не сойдётся бюджет M4 — 2K.
  - **За краем** — дымка. Земля за краем круга — «земля планеты» SkyAtmosphere, её цвет даёт туман. Без своего цвета туман берёт его от неба и выходит тёмно-синим — это и было «море» вокруг острова. Первый подбор в `level_krom.py`: плотность 0,03, спад 0,2, цвет рассеяния (0,25; 0,32; 0,42). Если дымка не спрячет край, запасные варианты: плоский «фартук» дальше круга или цвет земли планеты под цвет кольца.
- **Почему:** 15–18 км — компромисс владельца: озеро в кадре с высоты, а данные в одном тайле. WorldCover даёт узор полей, лесов и города без зашитого в снимок света, облаков и времени года. Палитру можно менять, а для v0.2/v0.3 город можно заменить полями. Меш с Nanite повторяет путь стен и героев (D-019, D-021) и не требует шагов в интерфейсе.
- **Альтернативы:**
  - Радиус 10 км: дельта обрезана, туман гуще. Радиус 25 км и больше: нужны ещё 2–3 тайла, а для ракурсов с земли это лишнее.
  - Второй грубый Landscape: дыра в центре через слой видимости и создание через интерфейс (D-015), кривизны нет.
  - Всё в редакторе, как стены: у Python редактора нет numpy и rasterio.
  - Blender — лишний шаг без выгоды. Cesium for Unreal (рельеф и снимки по сети) — зависимость от сети, чужой стиль, плагин под 5.8 не проверен. Панорама на цилиндре — в облёте видно, что это картинка.
  - Материал одним цветом — с высоты ровное покрывало, реки выше уреза пропадают. Снимок Sentinel-2 (S-32) — самый «настоящий», но цвета зашиты в снимок, трудно свести со стилизованным Landscape, и для прошлых эпох не годится (IDEAS).
- **Проверка:** в кадрах `zavelichye` и `oblique` не видно края мира и стыка с Landscape, поверх рек нет полос суши, бюджет VRAM — в пункте M4. 2026-09-25 по снимкам `zavelichye`, `oblique`, `olginsky` и нового `high_nw`: края мира и ступеньки на стыке нет, реки на месте. Цветовой стык виден: на Landscape пока подложка OSM, а город в кольце — класс «город», и граница идёт прямой линией по краю Landscape. С высоты у горизонта видна резкая граница между светлым небом и полосой дымки — это цвет неба и тумана, пункт M4 про небо и туман.
- **Последствия:** в `refs/` добавлены кропы `dem/fabdem_horizon.tif` (4,6 МБ) и `landcover/worldcover_horizon.tif` (1,5 МБ), оба в LFS. В атрибуцию проекта — ESA WorldCover (CC BY 4.0) рядом с FABDEM. Плоскость воды Landscape остаётся: на краю Landscape кривизна — 8 см. Материал Landscape в M4 должен брать цвета поля, леса и города из тех же параметров, что `M_KromHorizon` (общий родитель или общий набор параметров), иначе цветовой стык будет возвращаться при каждой правке палитры.

## D-024. Небо «ясный день»: облака движка, дымка в два слоя; свет и дымку подбирать по снимкам вьюпорта
- **Дата:** 2026-09-25 · **Статус:** Accepted
- **Контекст:** пункт M4 «Sky Atmosphere + Volumetric Clouds + Exponential Height Fog». После кольца горизонта (D-023) дымка была подобрана по снимкам SceneCapture (`shot_krom.py`). В настоящем вьюпорте с Lumen и автоэкспозицией та же дымка заливала всё белым, а по снимкам SceneCapture этого было не видно.
- **Решение:**
  - **Облака** — `VolumetricCloud` с материалом движка `m_SimpleVolumetricCloud`: слой 5–15 км из коробки, солнце отбрасывает тени облаков на землю.
  - **Дымка в два слоя** у `ExponentialHeightFog`. У земли — плотность 0,015, спад 0,2, свой цвет рассеяния: она растворяет край кольца. Высокий тонкий слой (`second_fog_data`) — плотность 0,0012, спад 0,02: затягивает небо у горизонта. Числа — в `level_krom.py`.
  - **Солнце** — 10 лк, как в шаблоне UE, экспозиция автоматическая. Цвет дымки задан в абсолютной яркости: если менять яркость солнца (пресеты времени суток), его меняют вместе с ней.
  - **Снимки для подбора света** — вьюпорт редактора: `view_krom.py` через `EditorAppToolset.CaptureViewport` (Unreal MCP). `shot_krom.py` остаётся для геометрии и сверки с фото.
- **Почему:** облака движка из коробки дают узнаваемое небо ясного дня с кучевыми облаками, настраивать нечего. Один слой дымки прижат к земле: лучи выше горизонта её почти не проходят, и с высоты между небом и дымкой видна черта. Второй слой эту черту снимает. Свет, подобранный по SceneCapture, в ролике выглядел бы иначе.
- **Альтернативы:**
  - Облака ниже, 1,8–2,5 км, как у настоящих кучевых: с материалом движка их меньше и они плоские.
  - Небо без объёмных облаков (плоский слой в материале неба) — дешевле, но при облёте не даёт параллакса и теней.
  - Цвет дымки от неба (`fog_inscattering_luminance` = 0) — у горизонта тёмная полоса.
  - Второй слой плотнее (0,004) — небо серое, облака размыты.
  - Не пробовали: `aerial_pespective_view_distance_scale` у SkyAtmosphere (дымка цветом самого неба) и солнце в физических люксах (≈100 000 лк).
- **Последствия:** облака — заметная доля кадра GPU. Замер не получился: `ProfileGPU` ловит кадр, где вьюпорт не рисуется. Он переходит в пункт M4 о бюджете. В снимках вьюпорта облака шумят: один кадр без накопления, в MRQ шум уйдёт. Режим вида (`viewmode unlit`) на `CaptureViewport` не действует. Пресеты времени суток строятся от этих настроек.
- **Уточнение 2026-09-25 (скорость):** вьюпорт с облаками заметно тормозит, владелец проверил: без облаков скорость вернулась. Поэтому в редакторе облака выключены (`CLOUDS_VISIBLE = False` в `level_krom.py`, видимость компонента сохраняется в уровне), для кадров их включает `view_krom.clouds(True)`, для рендера — скрипт рендера (M6). Кольцо горизонта дорого только на видах с высоты (много земли в кадре), тени от него ничего не стоят. Вьюпорт рисует в 100 % (`r.Editor.Viewport.ScreenPercentage`); 75 % по D-005 — запасной ход, если снова станет тесно.

## D-025. Земля Landscape — маска покрытия из OSM, текстуры CC0 и общая палитра `MPC_KromPalette`
- **Дата:** 2026-09-26 · **Статус:** Accepted (пункт M4 «Материалы: трава, земля»; выполняет последствие D-023 про общие параметры); край Landscape — D-038, уточнение 2026-09-27 «весь Landscape»
- **Контекст:** на Landscape до сих пор лежала подложка OSM — карта с чёрными дорогами и белыми кварталами. D-023 требует, чтобы Landscape и кольцо горизонта брали цвета поля, леса и города из одних параметров, иначе стык на краю Landscape возвращается при каждой правке палитры. Слои Landscape (weightmap) из Python не рисуются, а руками их рисовать — против правила «повторяемое — скриптами».
- **Решение:**
  - **Покрытие — маска из OSM**, как у кольца маска из WorldCover. `terrain_krom.render_mask` пишет `refs/dem/ground_mask_L_Krom.png` 2048² (≈1 м на пиксель) по мировым XY: R — грунт (тропы, стройки, площадки), G — мощение (тротуары, площади, руины фундаментов), B — асфальт (дороги, стоянки), A — здания; остальное — трава. Класс дорожки — по тегу `surface`, без него — по виду `highway` (тротуар — мощение, тропа — грунт, дорога — асфальт); правила — `osm_layers.ground`. Городские стены в OSM размечены и как `building` — пропускаются, под ними меши стен. WorldCover для Landscape не годится: двор Крома в нём — «застройка».
  - **Общая палитра — Material Parameter Collection `MPC_KromPalette`** (`palette_krom.py`): Field, Forest, Built, Water, Earth, Asphalt, Paved. Её читают `M_KromLandscape`, `M_KromHorizon` и `M_KromWater`. Пресеты времени суток смогут менять цвета на лету, без пересборки материалов. Параметры обновляются на месте, чтобы не менялись их GUID.
  - **Рисунок — текстуры Poly Haven (CC0, 2K, S-33)**, скачивает `textures_fetch.py`. В материале текстура делится на свой средний цвет и умножается на цвет палитры: рисунок от текстуры, цвет от палитры. Издалека земля ровно цвета палитры. Трава с крупными пятнами (та же текстура в 23 раза крупнее). Круче ≈32° и в полосе 0,8 м над урезом проступает грунт.
  - **Край Landscape** от 650 до 900 м от собора плавно переходит в вид кольца: та же маска WorldCover и те же цвета. Дальше 900 м нет и данных OSM (граница выгрузки).
  - Смешение — один узел Custom с HLSL в `landscape_krom.py`: граф из сотни узлов, собранный из Python, не читается и не правится.
- **Почему:** маска и HLSL целиком в скриптах и в git. Правка OSM или правил — перезапуск двух скриптов, без кисти. Один источник цвета лечит стык с кольцом и в будущем даёт пресеты времени суток. Poly Haven — CC0, скачивается по API, в отличие от Fab/Megascans (вход в аккаунт и загрузка через интерфейс редактора).
- **Альтернативы:** (1) слои Landscape с кистью — не скриптуется, веса в бинарных ассетах; (2) Megascans через Fab — лучше качество, но лицензия Fab и загрузка руками; (3) текстуры из ChatGPT Images — без нормалей и с неясной бесшовностью; (4) процедурный шум без текстур — вблизи земля как пластилин; (5) WorldCover и на Landscape — двор Крома выходит городом; (6) отдельные VectorParameter в каждом материале — стык возвращается при правке.
- **Проверка (2026-09-26, `view_krom`):** `oblique` — стыка Landscape и кольца по прямой не видно, город в кольце темнее; во дворе Крома и над Довмонтовым городом трава, мощёные и грунтовые дорожки читаются, повтор текстуры в глаза не бросается. Материал — 281 инструкция, 7 сэмплеров.
- **Последствия:** `T_KromMap` (подложка) материалом больше не используется, PNG остаётся для сверки. Нормали и шероховатость текстур пока не подключены (только цвет) — при виде с высоты глаз дальше в M4. Пятна зданий на Landscape выглядят площадками, пока в M5 не встанут дома. Порядок первичной сборки: `horizon_krom.py` раньше `landscape_krom.py` (край Landscape берёт `T_HorizonMask`).

## D-026. Перепад у Персей — в `terrain_krom`, высоты Landscape — скриптом `heights_krom`, у стен захаба — уровень двора
- **Дата:** 2026-09-26 · **Статус:** Accepted (уточняет D-014 и D-021; закрывает IDEAS «Перепад двор Крома — Довмонтов город у Персей»)
- **Контекст:** в heightmap Довмонтов город у Персей всего на 1–1,5 м ниже двора Крома, а по S-06 Перси со двора 6 м, со стороны Довмонтова города ≈15 м; владелец помнит подъём. FABDEM (шаг 30 м) уступа на самой стене не видит: на Y = 60 перепада нет вовсе, а на фото там 13 м кладки над дорогой. Обновить высоты Landscape можно было только через интерфейс (D-014).
- **Решение:**
  - **Рельеф** — `terrain_krom.persi_step`, отметки от земли двора за Персями (среднее в 25–40 м от стены, −2,3 от собора). Двор за Персями насыпной: до 10–20 м от стены поднят до этой земли. Уступ — посередине тела стены. К югу — ложбина бывшего рва (подошва −9,5, откос к газону на 4–12 м), газон Довмонтова города −7,75, к 90 м — прежний рельеф. У Великих ворот дорога −7,0, пол проезда ровный; захаб поднимается от ворот к двору. Бровка берега снаружи западной стены Довмонтова города и полоса 40 м к востоку от восточной — не выше газона (иначе стены по плану уходят в землю снаружи). Числа — константы `PERSI_*`, `GATE_*` с источниками (S-06, S-23, S-34); порог ворот измерен по фото с людьми (S-34), остальное с ним сходится.
  - **Высоты Landscape — скриптом** `heights_krom.py`: heightmap байтами (R, G) → render target RGBA32f → `landscape_import_heightmap_from_render_target`, на тиках редактора (текстура, шейдер и пересборка Landscape асинхронны), сверка выгрузкой в 400 точках. Интерфейс больше не нужен.
  - **Уровень двора участка** (`WallRun.level_at`, `krom_plan.LEVEL_AT`): у Персей, захаба и восточной стены вдоль захаба точки «двора» попадают в захаб, а он у ворот на 7 м ниже двора. Эти участки меряются от одной точки двора Крома (`KROM_YARD_AT`, к западу от захаба) — одно ровное звено. Пол проёмов — по земле у двора, поэтому Великие ворота стоят на дороге. Троицкая меряется от той же точки, тело до −8; Смердья — до −11.
- **Почему:** три независимых отсчёта сходятся на ≈9 м у подошвы (S-06, акт ГИКЭ у Смердьей, замер по фото), DEM здесь слеп — как у береговых откосов, где ему тоже не верим (D-014). Скрипт вместо интерфейса — рельеф правится так же, как всё остальное: правка чисел и перезапуск.
- **Альтернативы:** (1) компромисс разведки (газон −5,75, ворота −5) — ближе к DEM, но противоречит фото; (2) ровно опустить весь Довмонтов город — южные и восточная стены уходят под землю снаружи; (3) кисть Landscape (IDEAS «Доводка откосов») — не повторяется скриптом; (4) уровень двора стены — по земле у двора, как раньше, — Перси у ворот проваливаются на 7 м.
- **Проверка (2026-09-26, `view_krom`):** с дороги на Великие ворота кадр сходится с фото img4 (S-34); над Довмонтовым городом — как аэрофото aerial7; Завеличье и общий вид — без изменений. Ступень на грани стены издалека давала травяные клинья по стене (LOD Landscape огрубляет сетку) — уступ перенесён внутрь тела стены.
- **Последствия:** после правки `terrain_krom.py`: `heights_krom.py` → `walls_krom.py` → `heroes_krom.py` → `blockout_krom.py`. Предупреждения `walls_krom` «двор выше снаружи лишь в N %» у стен Довмонтова города и у восточной стены вдоль захаба ожидаемы. Неуверенно: форма к югу от 40 м, полоса к востоку от Довмонтова города (там город выше газона на 8 м — гип.), ложбина у Смердьей (по письму читателя там засыпана). Владельцу — один снимок у «Меча Довмонта»: высота стены над тропой (≈15 м — подошву на −9,5 оставить).
- **Уточнение к D-013 (2026-09-26):** всё загружено в редакторе через `LocationVolume` «LoadAll» (`level_krom.py`). Объём, загруженный из Python, редактор между запусками не помнит; после запуска его загружает `Krom/Content/Python/init_unreal.py` (проверено перезапуском: 64 прокси из 64).

## D-027. Материалы зданий — рецепт земли: цвет из палитры, рисунок, рельеф и шероховатость из текстур CC0; материал на каждый ключ цвета
- **Дата:** 2026-09-26 · **Статус:** Accepted (пункт M4 «Материалы: белёный плитняк, открытый плитняк, кровли, купола»; продолжает D-025)
- **Контекст:** герои и стены были в заглушках blockout `MI_BO_*` — ровный цвет без рисунка. Слоты материалов у героев (Blender) и стен (GeometryScript) уже названы по ключам `krom_plan.COLORS`, UV в метрах (`bl_krom.box_uv`, `wall_mesh`). Цвета зданий жили только в плане, цвета земли — в `MPC_KromPalette` (D-025).
- **Решение:**
  - **Цвета** остаются в `krom_plan.COLORS`, `palette_krom.collection()` кладёт их в `MPC_KromPalette` под ключами с большой буквы (Wall, Stone, Wood…). Одна коллекция на землю и здания: подбор цвета и пресеты времени суток — без пересборки материалов.
  - **Материал на ключ** — `M_Krom<Ключ>` в `/Game/Krom/Materials/Buildings` (`materials_krom.py`), 11 штук. Узел коллекции в material instance не параметризуется, поэтому не один мастер с MI, а маленький материал на ключ.
  - **Плитняк, побелка, тёс** — текстуры Poly Haven 2K (S-33): Rock Wall 08, Painted Plaster Wall, Old Planks 02 — цвет, нормали (DirectX), шероховатость. Цвет — как у земли: текстура делится на своё среднее и умножается на цвет палитры (у побелки остаётся 70 % рисунка). Рельеф ослаблен: плитняк 0,65 (в Крому швы залиты раствором, у текстуры камни «подушками»), побелка 0,4 (сильнее — на скользящем солнце зернит). Шероховатость — карта, сдвинутая к цели ключа. Повтор плитки 1,8–2 м гасит та же текстура в 6,7 раза крупнее.
  - **Металлы, стекло, крашеные кровли** — без текстур: позолота и оцинковка — металл (цвет = цвет отражения), колокола — наполовину, медь под патиной, крашеные кровли, тёмные главы и стекло — не металл; шероховатость — константы `MATS`.
  - **Числа цвета по фото** в одном свете на кадр (img4 — S-34, k21 — S-29, belfry_yard): белёное : плитняк : тёс ≈ 1,45 : 1 : 0,3. Побелка нейтральная (0,70), плитняк теплее (0,49; 0,46; 0,39), тёс серый (0,145), кровли собора и колокольни бирюзово-зелёные. Абсолют — правдоподобное альбедо (побелка 0,65–0,75, известняк 0,4–0,55).
  - **Назначение** — по имени слота на готовых мешах `/Game/Krom/Architecture`, геометрия не пересобирается. `heroes_krom` и `walls_krom` при пересборке берут те же материалы (`palette_krom.building_material`); `MI_BO_*` остаются у blockout (палаты, фундаменты).
  - **Доски тёса на кровлях стен — вниз по скату:** в `wall_mesh` UV ската строится по карнизу и уклону грани, а не проекцией по Z. Иначе у участков, идущих с запада на восток (Перси), доски шли вдоль стены. Шатры башен круче 45°, у них проекция и так вертикальная.
- **Почему:** рецепт земли — один источник цвета, рисунок без зашитого света, всё в скриптах и в git; правка — число и перезапуск. Poly Haven — CC0 и API (как в D-025).
- **Альтернативы:** (1) один мастер-материал с MI и цветом-параметром — цвета зданий выпадают из общей палитры; (2) triplanar по мировым координатам — UV в метрах уже есть, а на повёрнутых зданиях triplanar размывает ряды кладки; (3) plastered_stone_wall для побелки (камни под известью) — на фото собора и колокольни штукатурка гладкая; (4) Megascans — вход и загрузка руками.
- **Проверка (2026-09-26, `view_krom`):** ракурсы с высоты глаз (`yard_cathedral`, `yard_belfry`, `yard_kutekroma`, `yard_wall`, `gate_persi` — добавлены в `shot_krom.VIEWS`) и дальние. Кладка читается рядами, как на фото kutekroma_yard; повтор на стене 100 м в глаза не бросается; побелка без зерна; с реки стены светлые, как на фото через Великую.
- **Последствия:** порядок — `textures_fetch.py` → герои и стены → `materials_krom.py`. Касательные мешей не пересчитываются (`recompute_tangents` выключен): Nanite считает их сам, картинка верная; если рельеф поедет в запасном меше (`shot_krom`), — `set_lod_build_settings(recompute_tangents=True)`. Пологие тёсовые кровли героев — та же правка в `bl_krom.box_uv` (IDEAS). Blockout Довмонтова города — пока `MI_BO_*`.

## D-028. Пресеты времени суток — `light_krom.py`: день, рассвет в тумане, закат; экспозиция и тени облаков — часть пресета
- **Дата:** 2026-09-26 · **Статус:** Accepted (пункт M4 «Пресеты времени суток»; уточняет D-024)
- **Контекст:** свет и дымка «ясного дня» были зашиты в `level_krom.py` (D-024), а пересборка уровня пересоздаёт акторы. Для роликов M6 нужны рассвет в тумане и закат. Цвет дымки задан в абсолютной яркости (D-024), поэтому у каждого пресета он свой.
- **Решение:**
  - Пресеты — словарь `PRESETS` в `light_krom.py`; `apply(имя)` меняет свойства акторов «Sun», «SkyLight», «HeightFog», «Post» на месте. `level_krom.py` только ставит акторы и применяет `day`. Солнце задаётся азимутом и высотой, яркость одна на все пресеты (10 лк): цвет и ослабление низкого солнца даёт SkyAtmosphere.
  - **День** — как в D-024: солнце с юго-запада (азимут 225°, высота 35°).
  - **Рассвет в тумане** — солнце встаёт за Псковой (80°, 4°). Дымка у земли густая (0,12), прижата к воде (слой от уреза, спад 1,0); свечение вокруг солнца; объёмный туман на 1,5 км — лучи в дымке; −0,5 EV.
  - **Закат** — солнце садится за Завельем (280°, 3,5°): западные стены и собор в тёплом свете с Ольгинского моста и с устья. Дымка тёплая и тёмная (0,06; 0,045; 0,038); −0,8 EV.
  - **Экспозиция** — общий PostProcessVolume «Post» без границ; в пресете — абсолютная AutoExposureBias, у дня — 1,0 (умолчание UE5, с ним подбирался D-024). Без поправки при низком солнце автоэкспозиция вытягивает кадр в белёсое, и цвет заката пропадает. Дымка тут ни при чём: при плотности втрое меньше и без высокого слоя пелена та же.
  - **Тени облаков** у рассвета и заката выключены: при высоте солнца 3–4° слой облаков 5–15 км накрывает тенью весь Кром, и он гаснет под подсвеченными облаками. Сами облака остаются в кадре.
- **Почему:** пресет — набор чисел, переключается одной командой без пересоздания акторов, а в M6 те же акторы пойдут в Sequencer. Азимуты — по солнцу Пскова в конце лета и начале осени: восход ≈ 70–90°, закат ≈ 270–290° (57,8° с. ш.).
- **Альтернативы:** (1) три уровня или Data Layers со своим светом — акторы дублируются; (2) сразу ключи в Sequencer — ролика ещё нет; (3) цвет дымки от неба — тёмная полоса у горизонта (D-024); (4) ручная экспозиция EV100 — при облёте от земли к высоте всё равно нужна автоматическая.
- **Проверка (2026-09-26, `view_krom`, облака включены):** закат с Ольгинского моста и с устья — золотые стены, оранжевые облака, синяя вода; с Завеличья — светлый Кром на тёмной земле. Рассвет с Завеличья — солнце за собором в дымке; с устья — Кутекрома в тумане над водой. Кадры — `media/progress/2026-09-26_tod_*.jpg`.
- **Последствия:** числа света правятся только в `light_krom.PRESETS`; подбор без правки файла — `apply('sunset', fog=(…))`. Облака в снимках вьюпорта шахматят (не успевают сойтись) — для финала нужен MRQ (M6). Объёмный туман стоит времени GPU — он только у рассвета. В отражении воды на закате бывает вертикальный шов — задача воды M5. Бюджет M4 (`budget_krom.py`): видеопамять 2,7–3,8 ГБ из 4,6–5,2, стриминг без превышения; GPU 13 мс без облаков и 14–21 мс с облаками при вьюпорте 2032 × 1273, облака — ≈7 мс.

## D-029. Берега и дорожки — вторая маска покрытия (отсев, галька у уреза, наброска, настилы), полоса у уреза и берма под западной стеной
- **Дата:** 2026-09-26 · **Статус:** Accepted (M5 «Берега, деревья, газоны» — берега и дорожки; продолжает D-025 и D-026)
- **Контекст:** владелец: вокруг Крома «красивые пейзажи — дорожки, мостики, насыпи щебёнки». ## D-038. Дороги, тротуары и дорожки у Крома — геометрией поверх Landscape; сначала дорожки у Крома
- **Дата:** 2026-09-26 · **Статус:** Accepted (владелец: «им внимания практически не уделили», «субагенту доверить»; ответы на вопросы разведки — ниже); зона геометрии — весь Landscape: уточнение 2026-09-27 «весь Landscape» заменяет круг 650 м
- **Контекст:** автодороги, тротуары и дорожки — только класс покрытия в маске (D-025, D-029).   - **Геометрией в зоне 650 м** (меши по клеткам 250 м, Nanite, как город D-032): проезжая часть — лента с плоским сечением, перекрёстки — площадки по общим узлам OSM, бордюр правилом (15 см у улиц, 10 см у дворовых), тротуары на высоте бордюра, дорожки +2 см с «юбкой», лестницы проступями, «зебры» квадами. Зона геометрии теперь — круг `ZONE_M` **плюс контуры и линии `roads_mesh.EXTRA_ZONES`** с отступом: контур парка OSM 38938144 + 30 м и улица Воровского 61411359 (линия, ± 10 м) до края Landscape. Одни функции для геометрии и рельефа: `in_zone` (ленты, перекрёстки, площадки) и `zone_weight` (`terrain_krom.road_bed`); растры `RoadField`/`LandField` — прямоугольник `zone_bounds`. ## D-042. Превью облёта — в качестве реального времени; тяжёлый рендер только для финального ролика (уточняет D-033)
- **Дата:** 2026-09-27 · **Статус:** Accepted (владелец: «зачем нам превью, каждый кадр которой рендерится по нескольку секунд? Всё равно на движке в таком качестве никто пользоваться не будет»)
- **Контекст:** `render_krom.render()` по умолчанию — 4 временных сэмпла и прогрев 64 кадра: секунды на кадр, 90 с облёта — десятки минут. Для проверки маршрута, стыков и «что попало в кадр» это лишнее, а картинка не отражает того, что видит зритель в реальном времени.
- **Решение:** превью — `temporal=1, warmup=8`, 720p (`flyover_v2_rt`): минуты на весь облёт, качество — как в редакторе. Тяжёлые настройки (сэмплы, прогрев, 1080p) — один раз для финального ролика M6, когда маршрут и время суток утверждены владельцем.
- **Замер (2026-09-27):** MRQ внутри редактора (PIE) даже с одним сэмплом и без Game Override — 1,2 с на кадр (49 кадров/мин); старый захват Sequencer (`SequencerTools.render_movie`) пишет кадр с вьюпорта PIE меньшего размера — смазанные кадры, отброшен; **MRQ в отдельном процессе** (`MoviePipelineNewProcessExecutor`, `UnrealEditor-Cmd -game`) — 240 кадров за 17,6 с, ≈14 кадров/с. Превью = `render_krom.preview()` в отдельном процессе.
- **Последствия:** в README у `render_krom.py` — два режима; кадры превью «шумят» Lumen и облаками там же, где и вьюпорт, это норма для проверки.
- **Уточнение 2026-09-27 (стриминг):** в отдельном процессе (`-game`) World Partition грузит потоковые акторы по расстоянию от камеры, а не объёмом LoadAll, как в редакторе. Единственные потоковые акторы уровня — 64 прокси Landscape: в первые секунды облёта земля за Кромом отсутствовала и сквозь неё была видна плоскость воды (владелец: «часть земли вокруг собора под водой»; в превью v2 то же). Решение: все акторы уровня `is_spatially_loaded=False` (сцена 2 × 2 км целиком помещается в память, стримить нечего), `bc7040f`. Сопутствующее: у процесса рендера включён Remote Execution — `ue_run` выбирает редактор по PROBE (`259f021`), `init_unreal.py` без подсистем редактора молчит (`7093abb`).

## D-045. Сгенерированные ассеты UE — не в git; в репозитории исходники и скелет проекта
- **Дата:** 2026-09-27 · **Статус:** Accepted (владелец: «в гите хранить сгенерированные артефакты излишне, их же можно пересобрать»)
